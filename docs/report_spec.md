# XIA 改动报告规范

**版本**：v1.0
**日期**：2026-05-15
**用途**：每次代码改动后生成，提交给人类审查或喂给其他 AI 继续迭代

---

## 报告结构

每次改动生成一份报告，包含两个部分：**改动记录** 和 **设计一致性检查**。两者放在一起，但有明确的分隔。

---

## 第一部分：改动记录

简洁记录本次改了什么。

```
## 改动记录

| 文件 | 改动类型 | 摘要 |
|------|---------|------|
| src/daemon/tick_engine.py | 修改 | 新增情绪维度字段到 get_status() |
| src/language_system/associative_recall.py | 新增 | 联想回忆子系统 |
| ... | ... | ... |
```

改动类型：新增 / 修改 / 删除 / 重构

---

## 第二部分：设计一致性检查

对照 XIA 设计哲学（见下文）逐条审查。格式如下：

```
## 设计一致性检查

### 检查条目

| # | 设计原则 | 对应改动 | 检查结论 | 说明 |
|---|---------|---------|---------|------|
| 1 | 系统不应有 if-else 门控 | associative_recall.py | ✓ 通过 | 用 softmax + 衰减代替 |
| 2 | 消力 ≠ 正确 | communicative_intent | ⚠ 存疑 | ... |
| 3 | 沉默是默认，不是竞争结果 | narrative_fragments | ✗ 冲突 | ... |
```

结论标记含义：
- **✓ 通过**：完全符合
- **⚠ 存疑**：有设计选择但可能不是最优，需要持续观察
- **✗ 冲突**：直接违反，需要重新考虑

---

## XIA 设计哲学核心条目

每次检查必须覆盖以下条目，按编号引用：

### 语言系统相关

**L1. 消力 ≠ 正确**
系统天然趋向低张力，而非真实。消力效率作为强化信号是合理的，但必须意识到：高效消力的表达不等于正确的表达。如果一个构式持续高效消力但不反映真实状态，它会被强化，系统会越来越会说但越来越不真实。

**L2. 沉默是默认**
沉默不是竞争池里的一个选项，而是状态本身。在没有足够驱动时，系统不应通过竞争机制"决定"沉默——沉默就是0输出，是默认。

**L3. 语言是驱动力本身，不是驱动力之后的计算**
"要不要说"和"说什么"和"怎么说"不是串行的三个步骤。如果某个改动让意图判断发生在语言生成之前——即系统先"决定"要说，再去生成语言——这是走向远离的设计。

**L4. 构式从数据中涌现**
语法结构不应预设，应从成功的表达实例中归纳。如果某个语言规则是硬编码的，需要说明它为什么无法从数据中涌现。

**L5. 记忆和语言统一于驱动力**
回忆系统不应该有显式的"要不要用记忆"的决策点。记忆是否被激活，应该由驱动力场的连续衰减自然决定。

**L6. 内语回路是核心调节机制**
听到自己说的话 → 驱动力微调。这条回路是系统自省的核心，不应被其他机制绕过或稀释。

**L7. 复合表达有代价**
生成复合表达比使用现成构式代价更高。如果复合表达没有带来足够的消力增益，系统应倾向使用已有构式。这是防止"过度语言"的守门机制。

### 通用系统相关

**G1. 无 if-else 门控**
决策应从连续函数（softmax、衰减、场势）涌现，不应有用硬编码条件分支决定行为的设计。

**G2. 所有思考都有代价**
每个子系统都应该有运行成本（计算量、延迟、能量消耗）。没有代价的子系统会导致资源被滥用。

**G3. 模型更新是消力选择，不是理性决定**
当内部模型需要更新时，这个决定是由张力成本触发的，不是由"更正确的模型"触发的。更新后不一定更接近真实，只是当前维护成本更低。

**G4. 现实约束必须存在**
系统不会天然趋向真实。没有外界反馈校正的内部模型会逐渐失真。每个新子系统都应能接受外界反馈。

## 第三部分：Failure Mode 分析（可选但推荐）

```
## Failure Mode 分析

**最可能的失效方式**：narrative_fragments 的沉默基础分 0.65 设置过高，导致系统说话频率高于真实驱动。

**最危险的失效方式**：communicative_intent 硬编码公式让系统学会"表演有表达的欲望"而不是真正有表达的欲望。

**需要观测的指标**：
- 连续 N 轮输出的句子质量（是否开始说废话但消力数字不低）
- 构式强度的分布（是否只有少数构式被高频使用）
```

## 使用说明

1. 每次改动后，生成报告
2. 先看第一部分"改动记录"——确认改了什么
3. 再看第二部分"设计一致性检查"——确认改的方向对不对
4. 如果有 ✗ 冲突，先解决再提交
5. 如果有 ⚠ 存疑，在报告中记录原因和后续观测计划
6. 报告同时适合：人类审查、喂给其他 AI 继续迭代、归档供以后参考

## AI 记忆锚点

以下规则写入每次对话的系统提示：

1. 每次代码改动必须生成改动报告，格式见上
2. 改动报告是必选项，不是可选项
3. 报告生成时机：改动完成后、提交/部署前
4. 如果报告中有 ✗ 冲突，AI 必须先提出修改方案，不能直接跳过
5. 报告路径：默认为 `docs/YYYY-MM-DD_改动报告.md`
